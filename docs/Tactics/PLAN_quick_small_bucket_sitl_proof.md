# Quick 小筒精投 SITL 跑通计划

## 已证实的阻塞

- 默认 `min_drop_targets_required=1`，先识别中筒就结束搜索；强制收集 3 个候选时能选中半径约 0.075 m 的小筒。
- Gazebo 原生相机实测约 30 FPS，现有每帧调用 `gz topic --num 1 --json-output` 的桥接只发布约 3 FPS。小筒门禁 5 个不同帧/1 秒因此无法满足。
- `bucket_calibration_valid=false` 是真机安全锁：即使识别和伺服通过，也只准蓝盘兜底。
- 低空停止下降阈值约 1.72 m，释放窗口上界 1.70 m；必须观察是否稳定进入释放窗口。

## 方案

1. 将 SITL 图像桥接改为 Gazebo Transport 原生 Python 订阅，按最多 10–15 Hz 发布最新一帧，保留原始接收时刻用于新鲜度判断。启动桥接时禁用用户级 Python 包，避免其 protobuf 版本覆盖 Gazebo 系统绑定。实测 ROS 图像和视觉检测帧率。
2. bucket 搜索在仿真中至少积累全部 3 个候选再选最小半径；`blue` 保留现有搜索策略。最终实现应依据实际小筒目标条件结束搜索，不把“三个”硬编码成真机通用规则。
3. 只在 SITL 的受控实验中提供显式“名义标定”开关以测试小筒门禁。默认关闭，绝不复制到真机参数；记录采用的偏置/延迟/不确定度及其非物理验证性质。
4. 对释放高度和帧新鲜度做诊断，修正实际与设计不符的阈值交接；保留速度、配对、半径和单次释放安全条件。
5. 验收以日志出现 `release=small_bucket`、舵机服务确认、完整任务完成、视觉检测和半径窗口满足为准。SITL 舵机和投掷物未建真实落点模型，`small_bucket` 仅证明算法许可，不等于实际投中。

## 方案比较

- **原生 Gazebo 订阅（采用）：** 已实测 303 帧/10 秒；针对源头解决桥接吞吐。
- **放宽“五帧一秒”到两秒：** 能绕开 3 FPS，但削弱运动中半径一致性，不能证明原门禁设计可运行。
- **C++ ros_gz_image 桥接：** 现有脚本说明曾遇到 DDS 大消息问题，改造面更大；本轮优先验证原生 Python 路径。

本计划只用于 `Optimization` 的 SITL。`jetson` 分支和真机已验证的相机/伺服方向保持不动。

## 执行结果（2026-09-27）

已按上述方案实现并完成 SITL 验证。搜索改为等待经多帧半径证实的小筒，不要求固定收齐 3 个目标；图像改用 Gazebo 原生订阅加 JPEG ROS 话题，约 15 FPS。显式开启 SITL 名义标定后，日志记录 `small_bucket` 释放，完整任务达到 `COMPLETE`。投放瞬间的 Gazebo 真值几何核验见 [验证报告](REPORT_quick_small_bucket_sitl_2026-09-27.md)。这仍是名义落点验证，不是实体投掷物入桶试验。
