# Debug Log — 2026-07-09

## 问题

投放区 (CYLINDER_APPROACH) 总是不能成功逼近目标圆筒位置。

## 控制链追踪

投放区逼近的完整控制链：

```
VisionPipeline (YOLO+OpenCV)
  → CylinderDetection(center_u, center_v, center_x, center_y)
    → /drone/vision/cylinders (10Hz)
      → MissionFSM._cyl_cb() → _remember_cylinders() 记忆库
        → CylinderSelector.select() 选筒
          → CylinderApproachState._target_world_xy 记录目标世界坐标
            → execute():
              ├─ 目标可见: _goto_pixel_centered_target() 像素伺服
              └─ 目标丢失: _goto_target_xy() 记忆导航
                → fc.goto_ned(tn, te, -hold_alt)
                  → _StandaloneFlightFacade._publish_cmd()
                    → /drone/cmd_setpoint_ned (10Hz)
                      → px4_bridge._cmd_setpoint_cb()
                        → _control_loop 斜坡平滑 (20Hz)
                          → _offboard_heartbeat (10Hz)
                            → /fmu/in/trajectory_setpoint
                              → PX4 飞控
```

## 根因分析

### 根因 1（🔴 最可疑）：相机分辨率与 cx/cy 参数不匹配

**关键证据**：

`vision_params.yaml` 和 `mission_params.yaml` 都配置了：

```yaml
fx: 539.9
fy: 539.9
cx: 640.0    # ← 暗示图像宽度 = 1280
cy: 480.0    # ← 暗示图像高度 = 960
```

但 `gz_camera_bridge.py` 没有硬编码分辨率——它从 Gazebo 相机传感器读取原始分辨率：

```python
# gz_camera_bridge.py L52
w = frame.get("width", 0)   # ← 实际分辨率取决于 PX4 模型
h = frame.get("height", 0)
```

PX4 的 `gz_x500_mono_cam_down` 模型中的相机默认分辨率通常是 **640×480**（PX4 SITL 标准配置）。

如果实际图像是 640×480，参数 `cx=640, cy=480` 会产生灾难性后果：

```
实际图像中心: (320, 240)
配置的 cx/cy: (640, 480)  ← 指向图像的右下角之外

CylinderApproachState._pixel_error():
  du = cylinder_center_u - 640    ← 永远是巨大的负数 (~-300px)
  dv = cylinder_center_v - 480    ← 永远是巨大的负数 (~-200px)

_goto_pixel_centered_target():
  target_wx = drone_wx + (-300) * 5.0 / 539.9 = drone_wx - 2.78m
  target_wy = drone_wy + (-200) * 5.0 / 539.9 = drone_wy - 1.85m
```

**结果**：无人机以为圆柱永远在自己右下方 3 米处，于是每次都向错误方向飞行，永远无法收敛。

**验证方法**：

```bash
# 查看实际相机分辨率
gz topic -t "/world/drone_field/model/x500_mono_cam_down_0/link/camera_link/sensor/camera/image" \
  -e --num 1 --json-output | jq '.width, .height'

# 或查看 camera_bridge 日志
cat log/simulation_*/camera_bridge.log | head -5
```

### 根因 2（🟠 高概率）：像素→世界映射完全忽略无人机朝向

`CylinderApproachState._goto_pixel_centered_target()` 使用了**硬编码的轴映射**：

```python
# state_cylinder_approach.py L107-109
# 相机近似垂直向下: u→world x/east, v→world y/north.
target_wx = drone_wx + du * alt / fx
target_wy = drone_wy + dv * alt / fy
```

这里隐含了一个致命假设：**相机 x 轴始终指向东，y 轴始终指向北**。这只在无人机机头朝北（yaw=0）时成立。

实际情况：

```
无人机 yaw = 0° (朝北):    图像右→东 ✓,  图像下→北 ✓   ← 唯一正确的情况
无人机 yaw = 90° (朝东):   图像右→北,   图像下→西    ← 完全错误
无人机 yaw = 180° (朝南):  图像右→西,   图像下→南    ← 完全反向
无人机 yaw = -90° (朝西):  图像右→南,   图像下→东    ← 完全错误
```

在投放区扫描和逼近过程中，无人机的偏航角可能不是 0。特别是：
- PX4 的 Offboard 模式下 yaw 默认由 position controller 控制
- 如果 CYLINDER_SEARCH 扫描时改变了朝向，逼近阶段的 yaw 不会是 0
- Transition 飞行时 yaw 也会变化

**需要的修正**：

```python
import math
yaw = drone_current_yaw  # 从 telemetry 获取
# 将像素偏移旋转到世界坐标系
world_dx = du * math.cos(yaw) - dv * math.sin(yaw)
world_dy = du * math.sin(yaw) + dv * math.cos(yaw)
target_wx = drone_wx + world_dx * alt / fx
target_wy = drone_wy + world_dy * alt / fy
```

### 根因 3（🟠 高概率）：两套坐标系统互相矛盾

整个控制链中，圆筒目标有**两套独立计算的世界坐标**：

**路径 A：Vision Pipeline 的世界坐标（用于记忆和匹配）**

```python
# vision_pipeline.py L521-553
# 使用 CoordinateTransformer.pixel_to_world() 或 pixel_to_world_simple()
det.center_x = selected_xy[0]  # ← 可能是姿态补偿后的世界坐标
det.center_y = selected_xy[1]
```

存入 `known_cylinders` 记忆库，被 `CylinderSelector` 选择后传给 `CylinderApproachState._target_world_xy`。

**路径 B：Approach State 自己算的世界坐标（用于飞行控制）**

```python
# state_cylinder_approach.py L108-109
target_wx = drone_wx + du * alt / fx  # ← 完全没有姿态补偿
target_wy = drone_wy + dv * alt / fy
```

路径 A 使用姿态补偿（`pixel_to_world()` 包含完整的 6-DoF 射线求交），路径 B 使用简化 `du*alt/f`。**两者永远不可能完全一致**。

实际飞行中的矛盾场景：

```
1. Vision Pipeline 报告圆柱在世界坐标 (42.15, 3.92)
   → _target_world_xy = (42.15, 3.92)
   → 记忆库存储此坐标

2. Approach State 从像素误差算出目标在世界坐标 (42.08, 3.98)
   → fc.goto_ned() 飞向此处

3. 飞到 (42.08, 3.98) 后，圆柱在画面中偏左
   → _goto_pixel_centered_target 继续修正

4. 但如果圆柱在这个新位置仍不被 Vision Pipeline 的
   _find_nearest_cylinder() 匹配上（因为路径A的坐标略有不同）
   → target_cyl = None → 退化为记忆导航

5. 记忆坐标 (42.15, 3.92) ≠ 当前位置 (42.08, 3.98)
   → _goto_target_xy() 尝试飞回记忆坐标

6. 循环振荡或最终放弃（_memory_arrival_count >= 20 → ASCEND）
```

### 根因 4（🟡 中概率）：YOLO 检测抖动导致对心计数器不断重置

```python
# state_cylinder_approach.py L172-175
if pixel_error > tolerance_px:      # tolerance = 35px
    self._align_stable_count = 0    # ← 任意一帧超过 35px 就重置
else:
    self._align_stable_count += 1

# 需要连续 20 帧 (1秒) 全部 < 35px
if self._align_stable_count >= 20:
    return "DESCEND_TO_DROP"
```

YOLO 检测框在连续帧之间有固有的抖动（±5-15px 是正常的）。如果抖动幅度叠加任何轻微的姿态变化，`pixel_error` 很容易偶尔超过 35px 阈值，导致计数器**不断被清零**。

35px 在 5m 高度对应约 0.32m 的地面误差——对于正在靠近的无人机来说，这个容差相当紧。

### 根因 5（🟡 中概率）：max_acceleration 参数过大导致过冲振荡

```yaml
# mission_params.yaml
max_acceleration: 2.0    # ← 之前是 0.2，被改成了 2.0
```

在 `px4_bridge._control_loop` 中：

```python
max_step = max_acceleration * 0.05  # 2.0 * 0.05 = 0.1m/tick @ 20Hz
```

每次控制 tick 允许的最大 setpoint 步长是 0.1m。结合 approach state 每帧发布新的 `goto_ned`，setpoint 可能在 20Hz 下以每秒 2m 的速度变化。这会导致 PX4 的 position controller 出现**过冲**——无人机飞过目标位置，然后反向修正，再次过冲，形成振荡。

当 `max_acceleration` 从 0.2 改为 2.0（10倍），斜坡平滑基本失效，setpoint 几乎直接跳变。

### 根因 6（🟢 低概率但仍然可能）：投放区域边界钳制

```python
# state_cylinder_approach.py L111-114
if hasattr(self._fsm, "is_in_drop_zone_world"):
    if not self._fsm.is_in_drop_zone_world(target_wx, target_wy, margin=0.75):
        target_wx, target_wy = self._target_world_xy  # ← 强制拉回记忆坐标
```

如果像素误差算出的目标超出了投放区边界（例如因为根因 2 的方向错误），代码会**强制将目标拉回记忆坐标**，导致无人机在两个位置之间来回跳动。
